# Nateks Monitoring — инструкция ведения проекта

## 1. Главный принцип

Не восстанавливать историю из памяти. Перед работой использовать источники проекта и GitHub как источник актуального состояния проекта.

Порядок чтения:

1. `docs/TODO.md` — что делаем сейчас.
2. `docs/HISTORY.md` — что уже проверено и какие решения приняты.
3. `docs/OID-CATALOG.md` — какие OID найдены для каждой модели и что реально подтверждено.
4. Актуальные YAML/код — фактическая реализация.
5. При необходимости `docs/MONITORING_MODEL.md` — общая архитектура.

## 2. Главный рабочий цикл

В каждый момент времени иметь одну основную техническую цель.

Формат:

`Цель → текущий факт → один следующий эксперимент → проверка → фиксация результата → следующий шаг.`

Не переходить к следующему уровню, пока предыдущий не подтверждён.

Пример:

`Найти LLDP OID → проверить SNMP → получить значение → сопоставить с Web UI → записать OID → только потом менять Zabbix.`

## 3. GitHub — постоянная техническая память проекта

Репозиторий `newenergy86/NateksMonitoring` использовать не только как хранилище кода, но и как постоянную техническую память проекта.

**Ассистент должен самостоятельно вести журнал в GitHub. Пользователь не должен вручную переносить результаты в `HISTORY.md` или `OID-CATALOG.md`.**

После существенного эксперимента или принятого решения ассистент должен сам обновить соответствующий файл GitHub:

- `docs/HISTORY.md` — история экспериментов, факты, ошибки, решения и следующие шаги;
- `docs/OID-CATALOG.md` — найденные и проверенные OID;
- `docs/TODO.md` — текущее состояние задачи и следующий незавершённый этап.

Не ждать отдельной команды пользователя «запиши в журнал», если результат имеет значение для продолжения проекта.

Записывать также неудачные эксперименты: `Timeout`, `No Such Object`, неверные индексы, неработающие варианты LLD и другие результаты, которые предотвращают повторение работы.

Перед продолжением работы проверять эти журналы, чтобы не повторять уже проведённые эксперименты.

## 4. Не гадать по OID

OID считается рабочим только после успешного запроса к реальному устройству.

Для каждого нового OID фиксировать:

- модель устройства;
- версию прошивки, если известна;
- полный OID;
- назначение;
- индекс/формат индекса;
- команду проверки;
- фактический ответ;
- дату проверки;
- статус: `CONFIRMED`, `PARTIAL`, `FAILED`, `UNKNOWN`;
- источник: MIB, документация, существующий шаблон, код или эксперимент.

Если OID не работает — тоже записывать. Это предотвращает повторение уже проведённых экспериментов.

## 5. Каталог OID

`docs/OID-CATALOG.md` — единый журнал найденных OID.

Один и тот же OID может иметь разную семантику на разных моделях. Поэтому запись всегда привязывать к модели/прошивке.

Не переносить OID с NXI-3030 на NXI-3050 только потому, что они находятся в одном enterprise subtree.

## 6. Работа с Zabbix

Перед изменением шаблона:

1. определить конкретный item/discovery/prototype;
2. определить ожидаемый результат;
3. проверить OID отдельно через `snmpget`/`snmpwalk`;
4. только после успешной проверки менять YAML/Zabbix;
5. после изменения выполнить Test в Zabbix;
6. проверить созданные LLD-объекты/items;
7. записать результат в `HISTORY.md`.

За один этап менять только одну существенную вещь.

Не создавать новое discovery rule, если существующее можно корректно адаптировать.

Не удалять рабочую конфигурацию ради эксперимента: сначала сохранить экспорт.

## 7. LLD

Перед созданием или изменением LLD определить:

- что именно обнаруживаем;
- какой индекс является ключом строки таблицы;
- какие дополнительные макросы нужны;
- как индекс используется в item prototype;
- возвращает ли устройство реальные строки таблицы.

Если ручная подстановка индекса работает, а LLD не работает, не считать это доказательством правильности LLD. Сначала проверить структуру индексов и соответствие макросов.

## 8. Разделение NXI-3030 и NXI-3050

Старые NXI-3030 Legacy используют `NateksLegacyAdapter` для данных, недоступных удобным способом через SNMP. Это уже рабочая часть проекта.

NXI-3050 по возможности мониторить непосредственно через SNMP.

Адаптер не изменять для решения проблемы NXI-3050, пока не доказано, что необходимые данные невозможно получить через SNMP.

## 9. app.js

`app.js` — визуальный слой проекта.

Не менять `app.js`, пока соответствующие данные не будут корректно получаться и проверяться в Zabbix.

Сначала источник данных → затем Zabbix → затем Dashboard.

## 10. Проверка результата

Каждый технический вывод разделять на:

**Факт** — непосредственно подтверждён командой, Zabbix или устройством.

**Гипотеза** — предположение, которое ещё надо проверить.

**Решение** — принятое действие на основании подтверждённых фактов.

Не превращать гипотезу в факт только потому, что она логично выглядит.

## 11. После каждого существенного эксперимента

Ассистент самостоятельно фиксирует в GitHub короткую запись:

```text
Дата:
Цель:
Команда/изменение:
Результат:
Вывод:
Следующий шаг:
```

Неудачный тест также является результатом и должен быть сохранён.

## 12. Синхронизация репозиториев

Основной репозиторий:
`newenergy86/NateksMonitoring`

Адаптер:
`newenergy86/NateksLegacyAdapter`

Если изменение относится только к адаптеру — менять его репозиторий.
Если изменение относится к шаблонам, Dashboard или документации мониторинга — менять `NateksMonitoring`.

При зависимости между репозиториями фиксировать commit адаптера в журнале мониторинга.

## 13. Защита от потери контекста

Если в разговоре появляется фраза вроде «мы уже это проверяли», сначала искать подтверждение в `HISTORY.md` и `OID-CATALOG.md`, а не повторять эксперимент.

Если найденный ранее результат противоречит новому тесту — сохранить оба результата и выяснить причину. Старую запись не удалять.

Если задача изменилась — сначала обновить `TODO.md`, затем продолжать работу.

## 14. Минимизация лишней работы

Не делать одновременно:

- поиск OID;
- изменение YAML;
- изменение LLD;
- изменение Python/JS;
- изменение архитектуры.

Сначала установить причину проблемы, затем исправлять только необходимый слой.

Не переписывать работающий код без необходимости.

## 15. Критерий завершения этапа

Этап считается завершённым только когда:

1. решение воспроизводимо;
2. результат проверен на реальном устройстве или в Zabbix;
3. необходимые изменения внесены в актуальный файл;
4. результат записан в журнал GitHub;
5. `TODO.md` переведён на следующий этап.

## 16. Текущая приоритетная цепочка проекта

`Устройство → SNMP/HTTP → подтверждённые данные → Zabbix → LLD/items/triggers → Dashboard`

Не перескакивать через промежуточный слой без технической причины.

## 17. Формат общения

Пользователь предпочитает короткие ответы.

Давать только необходимую информацию. Не повторять уже известное. Если требуется действие пользователя — писать конкретно, что сделать. Сложные задачи разбивать на небольшие последовательные шаги.

После получения результата теста сразу определять следующий шаг.
