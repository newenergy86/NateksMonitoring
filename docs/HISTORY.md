# Nateks Monitoring — журнал решений и экспериментов

Этот файл ведётся автоматически в процессе работы над проектом. Пользователь не должен вручную переносить сюда результаты. Перед продолжением работы сначала проверять журнал.

## Правила записи
- Записывать существенные эксперименты, решения и изменения состояния задачи.
- Для SNMP сохранять команду, полный OID, фактический ответ и статус.
- Ошибки `Timeout`, `No Such Object` и другие неудачные проверки сохранять, чтобы не повторять их без причины.
- Разделять факт, гипотезу и принятое решение.
- После каждого существенного результата указывать следующий шаг.

## 2026-10-26 — восстановление состояния LLDP/NXI-3050

### Цель
Адаптировать существующий мониторинг NXI-3030 Legacy под NXI-3050 так, чтобы в Zabbix достоверно отображались LLDP-соседи: локальный порт, удалённое устройство, IP и удалённый порт. `app.js` до завершения настройки Zabbix не менять.

### Что подтверждено по источникам проекта

1. **NXI-3030 Legacy** использует vendor LLDP table:
   `1.3.6.1.4.1.4249.1.201.15.1.1.1.1`.
   В `app.js` зафиксирована структура полей:
   - field `1` — Local Port;
   - field `3` — Neighbor IP;
   - field `5` — Remote Port.
   fileciteturn397file0

2. В старом Zabbix-шаблоне присутствует стандартное `LLDP discovery` с OID `1.0.8802.1.1.2.1.3.7.1.3`, а также master item `LLDP Table` на нескольких стандартных LLDP OID. Наличие записи в YAML само по себе не является доказательством работы OID на NXI-3050.
   fileciteturn397file1

3. **NXI-3050** реально отдаёт vendor subtree `1.3.6.1.4.1.4249`, включая таблицу `1.3.6.1.4.1.4249.1.201.1.4...`.
   В частности, `1.3.6.1.4.1.4249.1.201.1.4.1.1.1.4.1.1` при ручной подстановке индекса вернул `INTEGER: 1`. Это подтверждает ответ данного OID, но пока не подтверждает его семантику как LLDP.

4. Полный `snmpwalk 1.3.6.1.4.1.4249` на NXI-3050 частично отдаёт данные, затем заканчивается `Timeout`. Поэтому полный walk нельзя использовать как доказательство отсутствия остальных таблиц.

### Проверки vendor interface table NXI-3050

Команда:
`snmpwalk -v2c -c pubsheksna -t 3 -r 0 10.0.110.10 1.3.6.1.4.1.4249`

В ответе подтверждены, среди прочего:
- `1.3.6.1.4.1.4249.1.201.1.4.1.1.1.1.1.1` → `INTEGER: 1`;
- аналогичные записи для портов/индексов 1–7;
- `1.3.6.1.4.1.4249.1.201.1.4.1.1.1.2.*` → значения вида `50659585`, `33686017`, ...;
- `1.3.6.1.4.1.4249.1.201.1.4.1.1.1.4.1.1` → `INTEGER: 1`.

Вывод: vendor interface table отвечает, но связь этих столбцов с LLDP пока не доказана.

### Web UI NXI-3050

LLDP на NXI-3050 подтверждён через `/ShowLldpPage`. Полученный HTML содержит, например:

```text
Local Port ID                    : Port_1/2
Remote Port ID<ifAlias>          : Port_9
Remote Chassis ID<MacAddr>       : 00:0f:d9:04:de:b8
Remote Management Address<IPV4>  : 10.0.110.18
Remote System Capability         : Bridge
Remote System Name               : sw-3030-kp-0km
Remote System Description        : NetXpertNXI-3030
```

Также в сохранённом `lldp.html` имеются соседи на `Port_1/1` и `Port_7/2`.
fileciteturn397file3

Это подтверждает наличие LLDP на устройстве, но не доказывает наличие соответствующего SNMP OID.

### Legacy Adapter

Для NXI-3050 ранее подтверждена авторизация через `/signin.html`, получение динамического `token`, CAPTCHA и успешное получение `/ShowLldpPage` через `curl --http0.9`. Обычный `requests` для ответа этой страницы не подходит из-за нестандартного HTTP/0.9-подобного ответа.
fileciteturn398file2

Это остаётся рабочим резервным способом получения LLDP, но текущая цель — по возможности получить те же данные непосредственно через SNMP/Zabbix.

### Важные решения

- Не менять `app.js` до стабильного получения LLDP в Zabbix.
- `Bridge Ports Discovery` относится к bridge/VLAN и сопоставлению портов; он не является источником LLDP и не должен использоваться как замена LLDP discovery.
- Не создавать новое LLD только из-за проблем с текущим discovery. Сначала определить, какой существующий механизм шаблона можно адаптировать.
- Не заменять весь шаблон целиком. Менять только подтверждённые OID/параметры.
- Не считать vendor OID `1.3.6.1.4.1.4249.1.201.1.4...` LLDP OID без отдельного доказательства.

### Следующий шаг

Продолжить поиск **реальной LLDP-таблицы NXI-3050** узкими SNMP-запросами. Основная задача — найти OID/таблицу, соответствующую данным `/ShowLldpPage`, и затем адаптировать существующий `LLDP Table` в шаблоне `Nateks_NXI_3050`.
