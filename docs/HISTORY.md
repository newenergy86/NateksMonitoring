## 2026-10-26 — адаптация NXI-3050 и LLDP

### Цель
Адаптировать мониторинг NXI-3030 Legacy под NXI-3050 так, чтобы в Zabbix достоверно отображались LLDP-соседи: локальный порт, удалённое устройство, IP и удалённый порт. До завершения настройки Zabbix не менять `app.js`.

### Подтверждено на NXI-3050 (10.0.110.10)
- SNMP v2c с указанными в тестах параметрами работает для vendor subtree `1.3.6.1.4.1.4249`.
- Рабочая таблица интерфейсов обнаружена по OID:
  - `1.3.6.1.4.1.4249.1.201.1.4.1.1.1.2` — значения IFINDEX.
  - `1.3.6.1.4.1.4249.1.201.1.4.1.1.1.4` — в ручных запросах обнаружены значения по индексам вида `1.1`, например `...1.4.1.1.1.4.1.1 = INTEGER: 1`. Семантику столбца нужно сверить с таблицей устройства; не считать его LLDP OID.
  - В выводе для `...1.4.1.1.1.1` доступны индексы портов 1–7 с повторяющимися конечными компонентами 1–4.
- Запрос subtree `snmpwalk ... 1.3.6.1.4.1.4249` возвращал часть vendor-таблицы, но завершался `Timeout` после первых значений `...1.4.1.1.1.3.1.1 = INTEGER: 1`. Это не доказывает отсутствие последующих OID: walk может остановиться из-за тайм-аута.
- Веб-интерфейс NXI-3050 действительно показывает LLDP-соседей. Зафиксированный пример: локальный порт `Port_1/2`, удалённый порт `Port_9`, IP `10.0.110.18`, имя `sw-3030-kp-0km`, описание `NetXpertNXI-3030`. Получение страницы `/ShowLldpPage` подтверждено через `curl --http0.9` с авторизацией/cookie.

### Не подтверждено / не использовать как факт
- Стандартные LLDP OID `1.0.8802.1.1.2.1.4.1.1.7`, `.8`, `.9` и subtree `1.0.8802.1.1.2.1.4.1` в текущих тестах завершались тайм-аутом или `No Such Object`. Значит, сейчас нельзя опираться на них как на рабочий SNMP источник NXI-3050.
- Vendor LLDP subtree `1.3.6.1.4.1.4249.1.201.15.1.1.1.1` используется парсером старого NXI-3030 в шаблоне и приложении, но для NXI-3050 не подтверждён. Прямой `snmpget` по `...15.1.1.1.1.1.1` получил `Timeout`.
- Не установлено, что стандартный LLDP отключён вообще: тайм-ауты могли возникать при отдельных запросах или из-за ограничения агента. Требуется проверка отдельными узкими запросами.

### Решения
- `app.js` не изменять, пока Zabbix не начнёт стабильно собирать LLDP.
- Не менять `Bridge Ports Discovery` ради LLDP: это отдельное обнаружение bridge-портов/сопоставления индексов, в старом шаблоне оно используется для VLAN.
- Не создавать дополнительные discovery rules без необходимости. Сначала изучить существующие элементы шаблонов и подтверждённый SNMP-вывод.
- Не подменять целиком шаблон. Изменения проводить по одному, после экспорта/резервной копии и тестирования.

### Исходники и точки правды
- Репозиторий мониторинга: https://github.com/newenergy86/NateksMonitoring
- Репозиторий адаптера: https://github.com/newenergy86/NateksLegacyAdapter
- В мониторинге шаблон 3030: `zabbix/templates/Nateks_NXI_3030_Legacy.yaml`.
- В актуальной рабочей копии пользователя есть `Nateks_NXI_3050.yaml`; на момент проверки в репозитории мониторинга его в дереве файлов не найден.
- В старом шаблоне LLDP Table использует vendor OID `...4249.1.201.15...`; это вариант только для 3030 до подтверждения на другой модели.
- Текущая версия в GitHub не обязательно совпадает с тем, что импортировано в живой Zabbix. Перед правкой зафиксировать, какой шаблон и экспорт действительно установлен.
